- **対象**：`.claude/plans/plans.md` の 5 章（5.1 ユニット、5.2 Functions、5.3 E2E）だけ

- **観点**：設計整合性（受け入れシナリオとテストの対応）

## P0（実装前に必ず直す）

### P0-01　前回の位置を使い続けることのテストがない
- **計画の記述**：U-mv-1〜5、E-1〜E-3 のどれにも「一度成功した後に GPS が失敗した」ケースがない
- **基準**：AC-8「位置の取得に失敗したときは、前回の位置を使い続ける」、F-1「位置の更新に失敗した場合は、前回の位置を使い続ける」
- **なぜずれるか**：AC にチェック項目として明記されているのに、対応するテストがない。実装で失敗時に位置を `null` に戻すと、POI と天気の取得が止まる。散歩中に GPS が途切れるのはよくあることなので、影響が大きい
- **追加するテスト**：
  - **U-loc-1**：成功 → timeout の順で、位置は前回のまま、ステータスは「失敗」、移動通知は出ない
  - **E-13**：成功の後に geolocation を失敗させて 60 秒進める → 座標の表示は変わらず、ステータスが「失敗」になり、住所選択は出ない（前回の位置があるため）

### P0-02　「東京で勝手に会話を始めない」のテストがない
- **計画の記述**：E-3 は「拒否 → 住所選択 → 選ぶ → 挨拶」の正常系だけを扱っている
- **基準**：AC-1b〔v1.1〕「初期選択は東京（東京駅）。ユーザーが選ばないうちに東京で会話を始めることはない」
- **なぜずれるか**：v1.1 で追加した安全側の基準（D-17）を守っているか確かめる、否定側のテストがない。既定値をそのまま位置として確定させる実装でも、E-3 は通ってしまう
- **追加するテスト**：
  - **E-14**：GPS を拒否して何も選ばずに 10 秒待つ → `/api/chat`、Overpass、Open-Meteo へのリクエストが 0 件で、住所選択で「関東 / 東京都」が初期選択になっている

### P0-03　「1km は 0 件、5km はあり」の経路にテストがない
- **計画の記述**：E-4 は「1km で 0 件 → 5km でも 0 件」だけを扱っている。U-op-8 は判定のロジックだけを見ている
- **基準**：AC-4「観光地が 1km 以内で見つからない場合、AI の返答に 5km エリアの提案も含まれる」、AC-4b の 1 項目め
- **なぜずれるか**：5km 検索の主な成功経路が、E2E でも Functions のテストでも検証されていない。クライアントが `radius: 5000` を送らない、またはサーバーのコンテキスト文に「5km 圏」と書かれない、という不具合を見逃す
- **追加するテスト**：
  - **E-15**：1km で 0 件 → 5km で 3 件 → `/api/chat` の本文が `pois.radius === 5000` かつ `kind === 'greeting'`。チップに 3 件が出る
  - **F-11**：`radius: 5000` のとき、コンテキスト文に「1km 以内には見つからず、5km 圏内」と書かれる

### P0-04　「クライアントに API キーが含まれない」のテストがない
- **計画の記述**：5 章には、ビルド成果物を検査するテストが 1 件もない
- **基準**：AC-9「クライアントのコードに API キーが含まれない」、4.4「API キーはサーバー側の関数だけが持つ」
- **なぜずれるか**：AC-9 のチェック項目が、検証されないまま残る。Vite は `VITE_` で始まる環境変数をバンドルに埋め込むので、命名を誤ると漏れる経路が現実にある
- **追加するテスト**：
  - **B-1**（ビルド検査。pre-commit ではなく `npm run build && npm run check:bundle`）：`dist/` の中に `sk-ant-`、`ANTHROPIC_API_KEY`、`x-api-key` が含まれず、`api.anthropic.com` も含まれない

## P1（推奨）

### P1-01　精度の閾値で、境界の片側しかない
- **計画の記述**：U-mv-2「精度 150m の測位は捨てる」
- **基準**：F-1〔v1.1〕「精度が 100m より悪い測位は捨てる」
- **なぜずれるか**：150m は境界から離れている。`>` を `>=` と書き間違えても検出できない
- **追加するテスト**：**U-mv-6**：accuracy が 100 なら採用、100.1 なら破棄

### P1-02　4 秒で打ち切る処理で、間に合った側のケースがない
- **計画の記述**：E-5 は 5 秒遅延（間に合わない側）だけを扱っている
- **基準**：F-2〔v1.1〕「応答を待つのは最大 4 秒」、AC-2〔v1.1〕
- **なぜずれるか**：境界の片側しかない。打ち切り時間が常に発動する実装（例：0 秒）でも E-5 は通る
- **追加するテスト**：
  - **E-16**：Overpass が 3 秒で応答 → 挨拶のリクエストに POI が含まれ、「周辺情報が届きました」は出ない
  - 合わせて **E-5** に「遅れて届いても `/api/chat` が再び呼ばれない」ことの確認を加える（D-12、3.3）

### P1-03　「1 件あれば OK」の境界がない
- **計画の記述**：U-op-8 は「0 件のときだけ 5km に進む」だけを扱っている
- **基準**：AC-2「1 件以上見つかれば OK（全カテゴリが揃う必要はない）」
- **なぜずれるか**：0 件と 1 件の境界が明示されていない。「カテゴリが揃わなければ広げる」という誤った実装を検出できない
- **追加するテスト**：**U-op-9**：1km でレストランが 1 件だけ → 5km 検索をしない（呼び出し回数が 1）

### P1-04　Overpass の失敗が、E2E で検証されていない
- **計画の記述**：U-op-7 と U-op-8 はユニットだけ。F-2 はサーバー側の文章だけ
- **基準**：AC-2「API が失敗したときは、AI がその旨を説明する。5km 検索には進まない」、F-7
- **なぜずれるか**：ユニットテストとサーバーのテストのあいだ（クライアントが `pois.status: 'error'` を送ること、5km へ進まないこと）が、結合した状態で検証されない
- **追加するテスト**：**E-17**：Overpass の 2 つのミラーがどちらも 500 → Overpass へのリクエストは 1km の 2 回だけ（5km はなし）。`/api/chat` に `pois.status === 'error'`、会話は続けられる

### P1-05　GPS の失敗の種類のうち、拒否しか扱っていない
- **計画の記述**：E-3 は拒否（denied）だけ
- **基準**：F-7「GPS の取得に失敗：前回の位置があればそれを使い、なければ住所選択を表示する」、AC-8
- **なぜずれるか**：timeout と unavailable は、拒否とは別の経路（ポーリングを続ける）で処理する設計（3.3）なのに、テストがない
- **追加するテスト**：
  - **U-loc-2**：エラーの分類（code 1 → denied でポーリング停止、code 2 / 3 → ポーリング継続）
  - **E-18**：初回から timeout で、前回の位置がない → 住所選択を表示

### P1-06　手入力から GPS に戻る処理が、E2E と通知で検証されていない
- **計画の記述**：U-mv-4「手入力から GPS 成功への切替」はユニットだけ
- **基準**：AC-1b〔v1.1〕「手入力の後に GPS が成功すると、GPS に切り替わって通知される」
- **なぜずれるか**：AC は「通知される」ことまで求めている。ユニットテストは切替の判定しか見ていない
- **追加するテスト**：**E-19**：timeout → 手入力で選ぶ → geolocation を成功させて 60 秒進める → ヘッダーが座標表示に変わり、GPS に戻ったことを知らせる通知が出る

### P1-07　「GPS を再試行」ボタンのテストがない
- **計画の記述**：なし
- **基準**：F-7〔v1.1〕「『GPS を再試行』ボタンも出す」
- **追加するテスト**：**E-20**：拒否 → 再試行ボタンが表示される → 権限を付与してボタンを押す → GPS で取得できてステータスが「成功」

### P1-08　ローディング表示（AC-5）がほとんど検証されていない
- **計画の記述**：E-4 で「範囲を広げて検索中」を確認するだけ
- **基準**：AC-5 の 1 項目めと 3 項目め（取得中のスピナー、AI が生成中のスピナー）、AC-2 の 1 項目め
- **追加するテスト**：**E-21**：外部 API を遅延させ、「現在地を取得中」「周辺を検索中」「考え中…」が順に表示され、完了したら消える

### P1-09　履歴の消去（F-5〔v1.1〕）のテストがない
- **計画の記述**：なし
- **基準**：F-5〔v1.1〕「『履歴をすべて消去』メニューを用意する（確認ダイアログあり）」
- **追加するテスト**：
  - **E-22**：消去 → キャンセル → 履歴が残る。消去 → OK → 画面と localStorage（messages、queue）が空になり、リロードしても戻らない
  - 消去の後に挨拶が再生成されるかどうかを仕様として決め、テストに書く（D-13 の「履歴がない」条件に当てはまるため、再生成する想定）

### P1-10　POI チップと「この辺りを教えて」ボタンのテストがない
- **計画の記述**：E-2 で「チップが更新される」ことは確認しているが、操作はしていない
- **基準**：F-2〔v1.1〕「項目をタップすると『〇〇について教えて』が入力欄に入る」、F-4〔v1.1〕「通知に『この辺りを教えて』ボタンを置く」
- **追加するテスト**：
  - **E-23**：チップを開いて項目をタップ → 入力欄に「〇〇について教えて」が入り、自動では送信されない
  - **E-24**：移動の通知にあるボタンを押す → `/api/chat` が 1 回呼ばれ、新しい位置のコンテキストが付いている

### P1-11　応答時間（AC-4、4.1）の検証手段がない
- **計画の記述**：5 章に性能のテストがない（`smoke` は 7 章に任意の項目としてあるだけ）
- **基準**：AC-4〔v1.1〕「最初の文字は 3 秒以内に表示され、通常の回答は 5 秒以内に出終わる」、4.1「起動から会話できるまで 5 秒以内」
- **なぜずれるか**：AC のチェック項目が、検証手段のないまま残る。実 API に依存するので自動の合否判定には向かないが、測る手段は必要
- **追加するテスト**：
  - **S-1**（`npm run smoke`、手動）：実際の Haiku に 5 回送り、最初の文字が届くまでの時間と、出終わるまでの時間の中央値を出力する。基準を超えたら警告する
  - **E-25**：モックが即座に応答する条件で、起動から挨拶の最初の文字が出るまで 1 秒以内（クライアント側の処理が予算を食いつぶしていないことを確認する）

### P1-12　市区町村データの妥当性テストが、5 章にない
- **計画の記述**：T3 の成果物の説明に「件数と座標範囲の検証テスト」とあるが、5 章のテスト一覧に載っていない
- **基準**：4.6〔v1.1〕（8 地方、全都道府県、政令市は区単位、代表座標）、AC-1b
- **追加するテスト**：
  - **U-data-1**：都道府県がちょうど 47
  - **U-data-2**：地方が 8 区分で、すべての都道府県がいずれかに属する
  - **U-data-3**：すべての座標が日本の範囲内（緯度 20〜46、経度 122〜154）
  - **U-data-4**：(都道府県, 市区町村) の組に重複がない
  - **U-data-5**：政令市は区単位になっている（例：横浜市の 18 区があり、「横浜市」単独の項目はない）
  - **U-data-6**：東京駅を初期値として選べる（D-17）

### P1-13　レート制限で、境界の片側しかない
- **計画の記述**：F-6「レート制限を超えた → 429」
- **基準**：4.4〔v1.1〕「IP ごとのレート制限（20 回 / 分）」、AC-9
- **追加するテスト**：**F-6** を書き換える。同じ IP からの 20 回目は 200、21 回目は 429。別の IP は 200

### P1-14　Origin ヘッダーがない場合の扱いが決まっていない
- **計画の記述**：F-5「Origin が許可リストにない → 403」
- **基準**：AC-9「許可していない Origin からのリクエストは 403 で拒否される」
- **なぜずれるか**：Origin ヘッダーそのものがない場合（curl などから直接叩かれた場合）の扱いがテストにない。プロキシの悪用対策（D-21）の抜け穴になる
- **追加するテスト**：**F-12**：Origin ヘッダーがない → 403。許可された Origin → 200

### P1-15　外部 API に丸めた座標が渡っているかの検証がない
- **計画の記述**：F-4 で検証しているのは `/api/chat` の 4 桁拒否だけ。U-geo-3 は丸め関数の単体テストだけ
- **基準**：4.4〔v1.1〕「Open-Meteo には小数 3 桁に丸めた座標だけを送る。Overpass には丸めた座標を中心に問い合わせる」
- **なぜずれるか**：プライバシーの要件のうち、Open-Meteo と Overpass に送る分が検証されない
- **追加するテスト**：**E-26**：geolocation を (35.681236, 139.767125) に設定 → Open-Meteo の URL にある latitude / longitude、Overpass のクエリにある `around` の中心、`/api/chat` の place が、すべて小数 3 桁以下

### P1-16　オフラインのキューがリロード後も残ることが、E2E で検証されていない
- **計画の記述**：U-q-4 はユニットだけ。E-8 はリロードしない
- **基準**：AC-7〔v1.1〕「送信待ちのメッセージもリロード後に残る」
- **なぜずれるか**：localStorage との結合（保存するキーの名前、起動時の復元の順番）が検証されない。なお、オフラインのままリロードするとアプリ自体が開かない（スコープ外、8 章）ので、テストはその制約の内側で組む必要がある
- **追加するテスト**：**E-27**：`/api/chat` を通信エラーにして送信 → 「送信待ち」→ 通信を戻さずにオンラインのままリロード（アプリ本体は配信される）→ 「送信待ち」が残っている → `/api/chat` を通るようにすると自動で送られる
