# 決定ログ

要件定義書 v1.0 から v1.1 への変更と、設計上の判断を記録する。
- 「元の質問」は、計画づくりのときの質問番号（Q2〜Q25）
- 「区分」が **合意** のものはユーザーが選んだ決定、**仮定** のものは「推奨案で」と一任された決定。仮定はあとから見直してよい

|---|---|---|---|---|
| D-01 | Q25 | 合意 | `poc` は複数の PoC を並べるモノレポにする。このアプリのファイルはすべて `location/` に置き、リポジトリ直下には何も置かない | ほかの PoC と依存関係や設定が混ざらないようにするため |
| D-02 | Q2 | 合意 | 締め切りは設けず、品質を優先する | — |
| D-03 | Q3 | 合意 | pre-commit で typecheck、lint、ユニットテストを強制する。E2E は手動。hook は husky で `location/.husky` に置き、`location/` 配下に変更があるときだけ実行する | lefthook は設定ファイルをリポジトリ直下に置く必要があり、D-01 と衝突するため。`core.hooksPath` はリポジトリ全体に効くので、ほかの PoC のコミットでは何もせずに終わるようにする |
| D-04 | Q4 | 合意 | `/api/chat` と Open-Meteo には小数 3 桁（約 100m）に丸めた座標を送る。サーバーは保存もログ出力もしない | 「座標をサーバーに送らない」と「AI に現在地を渡す」は両立しない。100m の誤差なら観光案内の質はほぼ落ちない |

| D-09 | Q9 | 合意 | Overpass はブラウザから直接呼び、失敗したらミラーに切り替える。4 秒待っても応答がなければ、先に挨拶する | 共有 IP のサーバー経由だとレート制限にかかりやすく、座標もサーバーを通ることになる。起動から 5 秒以内という要件を守るため |
