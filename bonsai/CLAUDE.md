# 盆栽育成ゲーム（bonsai）

PCブラウザで動く、水墨画風の3D盆栽ゲーム。種から実時間で約1週間（1時間に1ステップ、168ステップ）かけて木が育ち、剪定・針金・葉摘み・水やりで樹形を整え、5つの指標で樹形を採点する。作者1人が自分の手元で遊ぶためのもの。
`uchu-jin/poc` モノレポの中の 1 つの POC。**ファイルはすべて `bonsai/` の中に作り、リポジトリ直下（`../`）には何も置かない**。
要件定義: docs/requirements/requirements.md

## 技術スタック

- TypeScript（strict）＋ Vite（UI フレームワークなし）、HTML / CSS（隣の `location/`・`earth-from-satellites/` と同じ構成）
- 3D：Three.js。バージョンを固定して CDN から読み込む（バンドルに含めない）【要確認：版と読み込み方は最初のプランで決める】
- 配布物：ビルド結果を `dist/index.html` の 1 ファイルにまとめる（スタイルとスクリプトをインライン化）。書くときは `src/` で部品ごとに分ける
- 保存：ブラウザの localStorage のみ。サーバー・外部 API は使わない（Webフォントと Three.js の CDN だけはネットワークを使う。どちらも無料・キー不要）
- テスト：Vitest（単体）、Playwright（E2E。chromium と firefox）（仮置き）
- 公開しない。手元の開発サーバーか、ビルドした `dist/index.html` を開いて遊ぶ

## よく使うコマンド

コマンドは core-growth のプランで確定した（2026-10-25）。

- 依存を入れる：`npx -y npm@11 ci`（この環境の npm 10 は不具合で `npm install` が失敗する）

- 開発サーバー：`npm run dev`
- ビルド（1ファイル出力）：`npm run build`
- 単体テスト：`npx vitest run`
- E2E：`npx playwright test <ファイル>`
- Lint：`npm run lint`
- 時間を早めて確かめる：`?speed=3600`（1秒で1時間進む）、開発者ツールで `window.__bonsai.advance(hours)`

## ディレクトリ

- `src/core/` ：Rng／Clock／Tree／Evaluator／Store と、その下で使う定数（constants.ts）・型（types.ts）・ベクトル計算（vec.ts）。**Three.js にも DOM にも依存させない**（Node の Vitest でそのまま動かす）
- `src/render/` ：Renderer。Three.js による描画、シェーダー、クリック判定（枝・葉・土）
- `src/ui/` ：画面の配置、ツール切り替え、カメラ操作、設定メニュー
- `src/main.ts` ：組み立てと `window.__bonsai`
- `tests/unit/`、`e2e/` ：テスト
- docs/requirements/ ：要件定義（FR-xxx / SC-xxx で参照する）
- docs/rules/ ：判定基準となるルール（architecture / security / testing）
- docs/workflow.md ：開発手順と機能ごとの進み具合
- docs/adr/ ：設計判断の記録（ADR-NNNN で参照する。書き方は docs/adr/README.md）
- .claude/plans/ ：機能ごとのプラン（_template.md を複製して使う）

## 開発の進め方

- 開発手順（8段階）と機能ごとの進み具合：docs/workflow.md。各コマンドの終わりに、その機能の行を更新する。段階を飛ばすときは理由を「メモ」に書く
- 実装に入る前に、必ず .claude/plans/ にプランを作る（/plan）
- プランは8項目で書く：概要／背景／詳細設計／テスト影響範囲／新規テストケース／実装順／コミット前テスト実行／スコープ外
- 未確定の論点は【要確認】を付けて残し、推測で埋めない。要件定義で「（仮置き）」とした数値は、プランで変えてよいが変えた理由を書く
- 実装順には、タスクごとの担当モデル・サブエージェントを書く（単純作業は安価なモデル、成長・評価・シェーダーなどの中核ロジックは上位モデル）

## 設計判断のルール（ADR）

- 選択肢が2つ以上あり後から変えにくい判断は、調査を始めた時点で docs/adr/ に起票する（/adr、状態：調査中）。保存データの形（`bonsai.save.v1`）を変える判断は必ず ADR にする
- AIの提案は、検証するまで事実として扱わない。提案と検証結果（コマンド・出力・一次資料）を ADR の検証ログに追記する。過去のエントリは書き換えない
- 選ばなかった選択肢は、理由と再検討する条件を ADR に残す
- 「採択」「却下」「置換」にするのは人間だけ。採択されていない ADR に基づいて実装しない
- ADR の決定を実装した箇所には、コメントで `ADR-NNNN` と書き、ADR の「実装箇所」にも足す

## 実装のルール

- プランの実装順に従う
- プランにない変更が必要になったら、実装せず立ち止まって報告する
- 要件定義・プランの「スコープ外」に書かれたものは作らない
- 乱数は必ず `seed` から作る Rng を通す。`Math.random()` と `Date.now()` を `src/core/` で直接呼ばない（時刻は Clock に渡す）。同じ seed と同じ手入れで同じ木になること（FR-008）を壊さないため
- 描画のための値（補間中の長さ、墨のにじみ）は保存データに入れない

## テストのルール

- 先に失敗するテストを書き、失敗（Red）を確認してから実装する
- 最初から通ったテストは、実装済みかassertが弱いかを報告する
- 完了報告には、実行コマンドと出力を付ける
- 時間の経過は、偽の時計を Clock に渡して確かめる。実時間を待つテストを書かない
- コミット前に実行：単体テスト全件／影響する E2E のみ

## レビューのルール

- 指摘は P0（実装前に必ず直す）／P1（推奨）／P2（軽微）で分類する
- 指摘には「どの記述が・どの基準と・なぜずれるか」を添える
- 判定基準：docs/rules/、docs/requirements/

## 報告のルール

- 根拠を確認できないものは推測で埋めず「不明」と答える
- プランに書いていない判断は「実装時の判断」と明示する
- 見た目（水墨画風の表現）は自動テストで判定しきれない。スクリーンショットを添えて作者に確認してもらう

## 触らない場所

- リポジトリ直下（`../`）と、隣の POC（`../location/`、`../earth-from-satellites/`、`../ai-dev-kickoff/`）
- `package-lock.json` の手編集、`dist/` などビルドの生成物
- pre-commit フックは入れない【要確認：リポジトリの core.hooksPath が `location/.husky` を指しているため。earth-from-satellites と同じ扱い】
