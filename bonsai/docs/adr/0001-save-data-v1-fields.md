# ADR-0001：保存データ v1 の形（要件の例に足す項目と、節の参照のしかた）

状態：採択 ｜ 起票：2026-10-20 ｜ 決定：2026-10-21 ｜ 決定者：作者
関連：docs/requirements/requirements.md の FR-008・FR-016・FR-017・FR-019〜024・FR-042、付録 A.5、12章 #6／.claude/plans/core-growth.md

## 1. 問い

保存データ `bonsai.save.v1` の形を、最初の版で決めきる。要件の例（付録 A.5）には、剪定・針金・葉摘みの機能で必要になる情報が足りない。あとから項目を足すと `version` を上げることになる（docs/rules/architecture.md）ため、最初の版を作る「土台と成長のコア」で次の4点を決める。

1. 剪定の芽吹きブースト（以後24ステップ、側芽が枝になる確率2倍。FR-017）をどこに持つか
2. 節の `id` の振り方と、`parent` が何を指すか（剪定で節を取り除く。FR-016）
3. 針金 `wire` の中身（外れる `age` と曲げの量。FR-019〜022）
4. 葉摘みの情報（摘んだ葉、葉が「半分以下」の基準。FR-023・FR-024）を、追加の項目なしで表せるか

（起票時は 1 だけを問いにしていた。2026-10-21 のプランレビューで 2〜4 も同じ理由で今決める必要があると指摘されたため、問いを広げた。V-02）

前提・制約：
- 保存データは localStorage のキー `bonsai.save.v1` に JSON 1つ（FR-042）
- 保存データの形を変えるときは ADR を書き、`version` を上げる（docs/rules/architecture.md）
- 剪定でその節から先は `nodes` から取り除く（FR-016）
- 同じ seed と同じ手入れで同じ木になる（FR-008）
- 節ごとの描画の演出（にじみ・落下。FR-016・FR-038）と取り消し（FR-027）は、節を `id` で見分ける

判定基準：
- 後の機能（剪定・針金・葉摘み）で `version` を上げずに済む
- 剪定で節を取り除いたとき、取り残しや食い違い（`id` の使い回し、消えた節を指す情報）が起きない
- 読み込み時の検証（docs/rules/security.md）が単純に書ける

## 2. 選択肢

| #   | 選択肢 | 概要 | 出どころ | 見立て |
| --- | ------ | ---- | -------- | ------ |
| A   | 節に持つ | 節ごとに `boostUntil`・`wire` を持つ。`parent` は親の `id`。`id` は二度と使わない連番で、次の番号 `nextId` を保存データ直下に持つ | AI（claude-opus-5-5） | 採用（V-02） |
| B   | 保存データ直下に一覧で持つ | `boosts: [{ nodeId, until }]`・`wires: [{ nodeId, ... }]` を直下に持つ。`parent` と `id` は A と同じ | AI（claude-opus-5-5） | 不採用（V-02） |
| C   | `parent` を配列の位置で持つ | `id` を持たず、`parent` は `nodes` の添字 | プランレビュー（V-02） | 不採用（V-02） |

### V-02（2026-10-21）プランレビュー（設計整合性・運用・セキュリティの3観点）の指摘との突き合わせ
- 対象：選択肢 A・B・C／判定基準すべて
- AIの提案・主張：plan-reviewer（claude-opus-5-5）3体の指摘の要点
  - 「`parent` が配列の位置か `id` か、`id` の振り方が決まっていない。『最大の id + 1』だと剪定で最大の節が消えたときに `id` が使い回され、描画の演出や取り消しで取り違える」
  - 「`boostUntil` だけ先に決めても、`wire` の中身を後で決めれば同じ理屈で `version` を上げることになる」
  - 「側芽の窓（生まれて24ステップ以内）の外で切ると、2倍にしても確率0のままで、成木の剪定で芽が出ない」
- 検証方法：要件 FR-016・FR-017・FR-019〜024・FR-027・FR-038 と付録 A.5 を読み、各案で何が起きるかを書き出した（コードはまだない）
- 結果：
  ```
  C（添字）：剪定で配列を詰めると、残った節の parent をすべて付け替える必要がある。
             描画・取り消しが節を見分ける手段もなくなる → 判定基準2を満たさない
  A／B の id：nextId を保存すれば使い回しは起きない。nextId がないと、読み込み後に
             「最大の id + 1」からやり直すしかなく、剪定直後に保存・再読み込みすると使い回す
  A の boostUntil・wire：節を取り除くと一緒に消える。検証は節ごとに閉じる
  B：剪定のたびに boosts・wires から消えた nodeId を取り除く処理が要る。
     取り除き忘れても検証で見つけるには一覧と nodes の突き合わせが要る
  葉摘み：摘んだ葉は leaves に残し regrowAt を入れる（付録 A.5 の形のまま）。
         「半分以下」の基準を「付きうる最大数」にすれば、節の数と葉の付き方から計算でき、
         項目は要らない。「直近の最大数」を選ぶと項目が要る（12章 #3）
  ブーストの効き方：側芽の条件を「(生まれて24ステップ以内 または boostUntil > age) かつ 子が1つ以下」
         にすれば、古い枝の切り口でも芽が出る
  ```
- 判定：一部確認 ― 文書の上での突き合わせ。実際に剪定・再読み込みで `id` が使い回されないことは、Store と剪定の単体テストで確かめる

## 4. 決定
（状態を「提案」にするときに AI が推奨を書き、作者が採択するときに確定する）

作者が AI の推奨どおり採択した（2026-10-21）。

- 採用：選択肢 A
  - 節に `boostUntil: number | null`（ブーストが切れる `age`。剪定の機能まで常に null）
  - 節に `wire: null | { until: number, axis: [x, y, z], angle: number }`（外れる `age`、その節で曲げた回転軸（長さ1）と角度（ラジアン、0〜π））。枝全体の曲げ量（120度の判定）は、枝の節の `angle` の合計で求め、保存しない
  - `parent` は親の `id`（根元は −1）。`id` は 0 からの連番で、二度と使わない。次に振る番号 `nextId` を保存データ直下に持つ。`nodes` は `id` の小さい順に並べる
  - 葉は付録 A.5 のとおり `{ size, regrowAt }`。摘んだ葉は一覧に残し、`regrowAt` に生え直す `age` を入れる。葉が「半分以下」の基準は「付きうる最大数」とし、保存しない（12章 #3 は葉摘みのプランで作者が決める。「直近の最大数」を選んだときは、この ADR を置換する）
- 理由：
  - 後の機能で `version` を上げずに済む → 剪定・針金・葉摘みが使う情報がすべて形に含まれる（V-02）
  - 取り残し・食い違いが起きない → 節を取り除けば、その節の情報も一緒に消える。`nextId` で `id` の使い回しもない（V-02）
  - 検証が単純 → 節ごとに閉じた検証で済む（V-02）
- 受け入れるトレードオフ：節1つあたりの JSON が少し大きくなる（`boostUntil`・`wire` の null が節の数だけ並ぶ）。節3,000個でも localStorage の容量（約5MB）に収まる見込みだが、実測していない
- 見直す条件：保存データが localStorage に収まらなくなったとき／葉摘みのプランで「半分」の基準に「直近の最大数」を選んだとき

## 5. 選ばなかった選択肢

### 選択肢 B：保存データ直下に一覧で持つ
- 選ばなかった理由：剪定のたびに一覧の掃除が要り、取り残しを検証で見つけるにも突き合わせが要る（V-02）
- 採らないことで失うもの：いまブーストや針金が付いている節を、節の一覧を全部見ずに数えられる（針金の同時8本の判定が少し楽）
- 再検討する条件：針金・ブーストの一覧を毎フレーム参照する必要が出て、全節を見る費用が問題になったとき

### 選択肢 C：`parent` を配列の位置で持つ
- 選ばなかった理由：剪定で詰めるたびに参照の付け替えが要り、節を見分ける手段もなくなる（V-02）
- 採らないことで失うもの：`id` と `nextId` の分だけ JSON が小さい
- 再検討する条件：なし
