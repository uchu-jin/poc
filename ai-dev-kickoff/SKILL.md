# AI駆動開発キックオフ

「プロフェッショナルAI駆動開発」の考え方に沿って、**AIにいきなり実装させず、要件定義とプランを軸に開発を進める**ための土台を作る。

貫く思想（生成物すべてに反映すること）:

| 思想 | このスキルでの具体化 |
|---|---|
| 上流で潰す | 実装前に要件定義・プランを作り、レビューしてから実装する |
| AIの暴走を型で防ぐ | 【要確認】タグ、スコープ外の明記、「プランにない変更は立ち止まって報告」 |
| 出力を検証可能にする | FR/SC の番号付け、P0/P1/P2 分類、テストログの提示、ADR の検証ログ（AIの提案と検証結果を分けて追記） |
| 最終責任は人間 | AIは質問役・説明役。確定と承認は人間 |

## 全体の流れ

```
Step 0  入口      サービス名と機能説明を受け取る
Step 1  インタビュー  質問ラウンドで要件を掘り出す（AIが質問、人間が答える）
Step 2  生成      CLAUDE.md / requirements.md / 土台一式を書き出し、最後に workflow.md（開発手順と進み具合）を書く
Step 3  確認      【要確認】の一覧と次の一手（/plan）を伝える
```

## Step 0: 入口

最初に必要なのは2つだけ:

1. **サービス名**
2. **機能説明**（何をするサービスか。箇条書きでも数行の文章でもよい）

ユーザーのメッセージに両方含まれていればそのまま Step 1 へ。足りなければこの2つだけを先に聞く。ここで他の質問を混ぜない。

あわせて**出力先ディレクトリ**を決める:

- **POC モノレポの中で使われた場合**（作業ディレクトリかその親に `ai-dev-kickoff/` があり、直下に `location/` などのアプリのフォルダが並んでいる。例: `uchu-jin/poc`）: リポジトリ直下に `<サービス名のスラッグ>/` を新しく作る。スラッグは英小文字とハイフンで、ユーザーに確認する。既存のアプリのフォルダや直下のファイルには触らない。
- **既存プロジェクトの中で使われた場合**: そのプロジェクトのルート。
- **どちらでもない場合**: `~/Desktop/<サービス名のスラッグ>/` などを提案する。

既に `CLAUDE.md` や `docs/requirements/requirements.md` があるなら、上書きせず「追記・更新」として扱い、変更前に差分方針を伝える。

## Step 1: インタビュー

`references/interview.md` を読み、質問バンクから**この案件で効く質問を選んで**聞く。全部を機械的に聞かない。

進め方のルール:

- **ラウンド制**: 1ラウンド3〜4問。ラウンドは「A. プロダクトの核 → B. MVPのスコープ → C. 受け入れ基準 → D. 技術と非機能 → E. 開発運用」の順。
- **AskUserQuestion ツールが使えるなら使う**。選択肢は機能説明から推測した具体的な候補にし、推奨があれば先頭に「(推奨)」を付ける。自由記述が要る問いはテキストで聞く。
- **答えにくい質問ほど価値がある**。エッジケース、トレードオフ、「やらないこと」、失敗時の振る舞いを必ず聞く。人間が曖昧にしている箇所を掘り出すのが目的。
- **前の回答を踏まえて次を聞く**。回答から新たに生まれた論点は次ラウンドで深掘りする。
- **「わからない」「後で決める」は正当な回答**。推測で埋めず【要確認】として記録する。
- ユーザーが「おまかせ」「デフォルトで」と言った項目は、`references/interview.md` の既定値を採用し、それが仮置きであることを生成物に書く。
- 各ラウンドの終わりに、そこまでで確定した内容を3〜5行で要約して見せる（誤解をその場で直せるように）。
- 質問が尽きたら（目安 4〜6ラウンド）、Step 2 に進む前に「これで書き出してよいか」を一言確認する。

## Step 2: 生成

### 2-1. 静的な土台を配置する

```bash
bash <このスキルのディレクトリ>/scripts/scaffold.sh <出力先ディレクトリ>
```

既存ファイルは上書きしない（スキップしたものは出力に表示される）。配置されるもの:

```
<project>/
├── CLAUDE.md                     ← 2-2 で書く
├── docs/
│   ├── requirements/requirements.md  ← 2-3 で書く
│   ├── workflow.md               ← 2-4 で書く（開発手順と進み具合）
│   ├── adr/                      設計判断の記録（ADR）
│   │   ├── README.md             書き方・状態・コードからの参照ルール・一覧
│   │   └── _template.md          ADR のひな形（問い／選択肢／検証ログ／決定／選ばなかった選択肢／実装箇所）
│   └── rules/
│       ├── architecture.md       判定基準（アーキテクチャ）
│       ├── security.md           判定基準（セキュリティ）
│       └── testing.md            判定基準（テスト）
└── .claude/
    ├── plans/_template.md        プラン8項目のひな形
    ├── agents/                   レビュー用サブエージェント
    │   ├── plan-reviewer.md
    │   ├── test-coverage-reviewer.md
    │   ├── design-reviewer.md
    │   ├── edge-case-reviewer.md
    │   └── security-reviewer.md
    └── commands/                 8段階ワークフローのスラッシュコマンド
        ├── plan.md           1. インタビュー式プラン作成
        ├── review-plan.md    2. プランの観点別レビュー
        ├── review-tests.md   3. テスト網羅レビュー
        ├── implement.md      4. 実装
        ├── test.md           5. テスト実装と全通過
        ├── review-impl.md    6. 実装の並列レビュー
        ├── explain.md        7. 人間のレビュー（壁打ち）
        ├── refactor.md       8. テスト駆動リファクタリング
        └── adr.md            どの段階でも：ADR の起票・検証・提案
```

### 2-2. CLAUDE.md を書く

`assets/CLAUDE.md.tmpl` をベースに、インタビュー結果で `［ ］` を埋めて `<project>/CLAUDE.md` に書く。

- **短く、全機能に共通することだけ**。機能固有の話は requirements.md やプランへ。
- 技術スタック・コマンド・ディレクトリは回答に合わせて書き換える（テンプレの Vitest/Playwright は既定値にすぎない）。
- 未決の項目は消さずに【要確認】を付けて残す。
- 「触らない場所」は回答がなければ一般的なもの（`.env*`、ロックファイルの手編集、自動生成ファイル）を置く。
- モノレポの中のアプリなら、冒頭に「ここは `<リポジトリ名>` モノレポの中の1つの POC。**ファイルはすべて `<スラッグ>/` の中に作り、リポジトリ直下（`../`）には何も置かない**」と書く。

### 2-3. requirements.md を書く

`assets/requirements.md.tmpl` の構成で `<project>/docs/requirements/requirements.md` に書く。

- ユーザーストーリーは優先度 P1（MVP必須）/P2/P3 を付け、各ストーリーに Given/When/Then の受け入れシナリオを付ける。
- 機能要件は `FR-001` から、成功基準は `SC-001` から通し番号。後工程のプラン・レビュー・テストがこの番号で参照する。
- 各 FR はテスト可能な一文にする（「〜できること」ではなく「〜したとき〜となる」）。
- **スコープ外**は必ず埋める。インタビューで出た「やらないこと」「v2以降」をすべて書く。
- 未確定の論点は本文中に【要確認】を付け、末尾の「未確定事項」表にも集約する。
- インタビューで出ていない内容を創作しない。補った箇所は「（仮置き）」と明記する。

### 2-4. workflow.md を書く（要件定義のあと）

requirements.md を書き終えてから、`assets/workflow.md.tmpl` をベースに `<project>/docs/workflow.md` を書く。開発手順の正本であり、機能ごとの進み具合の記録でもある。

- 「開発手順（8段階）」と各ルールはテンプレのまま使う。コマンド名を変えた場合だけ合わせる
- 「機能ごとの進み具合」には、requirements.md の **P1 のストーリー**を1行ずつ「段階 0／未着手」で並べる。「要件」列にストーリー番号と FR 番号、「次の一手」に `/plan <機能名と概要>` を書く
- 複数のストーリーをまとめて1つのプランにするのが自然なら（例：サーバー側と画面側に分ける）、そう分けてよい。分け方は Step 3 で作者に伝える
- P2・P3 のストーリーは並べない（MVP のあとに足す）

### 2-5. ADR を起票する（必要なときだけ）

インタビューで「迷っている」「おまかせ」となった後から変えにくい選定（技術スタック、ホスティング、外部APIなど）があれば、`assets/scaffold/docs/adr/_template.md` の形で `docs/adr/0001-<スラッグ>.md` から起票する。

- 状態は「調査中」。このスキルでは検証まではしない。問い・前提・判定基準・選択肢（出どころ付き）だけ書き、インタビューで出た理由は検証ログに「作者の回答」として残す
- 作者がはっきり指定し、迷いのない選定は ADR にしなくてよい（CLAUDE.md の技術スタックに書けば足りる）
- 起票したら docs/adr/README.md の「一覧」に行を足し、requirements.md の未確定事項表から ADR 番号を参照する

### 2-6. rules を調整する

`docs/rules/*.md` は汎用の初期値。インタビューで技術スタックや制約（個人情報の扱い、認証方式など）が出ていれば、該当ルールに数行追記する。出ていなければそのままでよい。

## Step 3: 確認と引き継ぎ

最後にユーザーへ短く伝える:

1. 作成・スキップしたファイル（リンク付き）。docs/workflow.md の「機能ごとの進み具合」の行も見せ、分け方がこれでよいかを一言確認する
2. **【要確認】の一覧**（requirements.md の未確定事項表と同じもの）と、起票した ADR（あれば）。ADR は `/adr <番号> 検証` で調査を続けられること
3. 次の一手: 最初に作る機能（P1 のストーリー）について

   ```
   /plan <機能名>
   ```

   を実行するとインタビュー式でプランが作られ（モノレポの場合は、`<スラッグ>/` を Claude Code で開き直してから。そのフォルダの `.claude/commands` が読み込まれるため）、そこから `/review-plan` → `/review-tests` → `/implement` → `/test` → `/review-impl` → `/explain` → `/refactor` と進められること。小さな修正では全段階を踏まなくてよいが、飛ばすときは docs/workflow.md の「メモ」に理由を残すこと、各コマンドの終わりに AI が進み具合を更新することも一言添える。

## 注意

- このスキルの成果物は「土台」まで。アプリのコード（`src/` の中身、パッケージの初期化）はユーザーが求めない限り作らない。初期化を求められたら、それも `/plan` で計画してから行う。
- CLAUDE.md は育てるもの。「AIが同じ間違いを繰り返したら1行足す」運用を伝える。
- 既存プロジェクトに `docs/decisions.md` のような決定ログが既にあるなら、ADR に移し替えない。そのまま残し、これから先の後から変えにくい判断だけを ADR にする（docs/adr/README.md に既存ログの場所を一行書く）。
