# インタビュー質問バンク

案件に合わせて**選んで・言い換えて**使う。機能説明から答えが明らかな問いは飛ばす。
各問いの「→」は、回答が生成物のどこに入るか。

## ラウンドA: プロダクトの核

- 誰の、どんな困りごとを解決するか。今その人はどうやって凌いでいるか？ → requirements「背景・課題」
- 主なユーザーは誰か。ユーザーの種類（ロール）は複数あるか？（例: 一般ユーザー／管理者） → 「ユーザーとロール」
- このサービスが「うまくいっている」とわかる数字は何か？（例: 作業時間が半分、週次利用率） → SC
- 似たサービスとの違いを1行で言うと？ → 「概要」
- 【答えにくい】このサービスが無くても困らない人は誰か。逆に一番困る人は？

## ラウンドB: MVPのスコープ

- 最初のリリースで「これが無いと出せない」機能を3つまでに絞ると？ → P1ストーリー
- その次に欲しい機能は？ → P2/P3
- 【答えにくい】やりたいが**v1ではやらない**と決めることは？ → スコープ外
- 【答えにくい】最初のユーザーは何人くらいか。社内/知人だけか、一般公開か？ → 非機能・セキュリティ
- ログイン・アカウントは必要か？ 必要なら方式は？（メール+パスワード／ソーシャル／マジックリンク／不要）

## ラウンドC: 受け入れ基準とエッジケース

P1ストーリーごとに:

- 正常にうまくいったとき、ユーザーは画面で何を見るか？ → Given/When/Then
- 【答えにくい】入力が空・不正・大きすぎるときはどうなるべきか？ → FR（異常系）
- 【答えにくい】途中で失敗したら（通信断、外部APIエラー）どう振る舞うか。データは残すか？
- 【答えにくい】同時に2人が同じものを編集したら？ 削除したものは復元できるべきか？
- 上限値はあるか？（件数、ファイルサイズ、文字数、回数） → 境界値テストの根拠
- AI/LLM機能がある場合: 出力が間違っていたとき人間がどう気づき、どう直すか？ AIの出力を確定扱いにしてよいか？

## ラウンドD: 技術と非機能

- 形態は？（Webアプリ／モバイル／CLI／API／Chrome拡張 など）
- 技術スタックの希望・制約は？（言語、フレームワーク、DB、ホスティング）「おまかせ」なら既定値を提案
- 外部サービス連携は？（決済、メール、OCR、LLM API など）APIキーの管理方法は？
- 扱う個人情報・機密情報は？ → rules/security.md
- 速度・可用性の期待は？（「数秒以内に表示」程度でよい）
- 【答えにくい】月額コストの上限は？ 外部APIの従量課金が上限を超えたら止めるか、許容するか？

## ラウンドE: 開発の運用

- 開発するのは自分一人か、チームか？ コードレビューは誰がするか？
- テストはどこまで書くか？（単体のみ／単体+E2E）
- AIに任せたくない領域はあるか？（例: 決済まわり、DBマイグレーション）
- 触ってほしくないファイル・ディレクトリは？
- ブランチ運用・コミットメッセージの規約はあるか？

## 「おまかせ」時の既定値

回答が「おまかせ」のときに提案する既定値。採用したら生成物に「（仮置き）」と書く。

| 項目 | Webアプリの既定値 |
|---|---|
| 言語 | TypeScript |
| フレームワーク | Next.js (App Router) |
| DB / ORM | PostgreSQL / Prisma（ローカル試作なら SQLite） |
| 認証 | 必要時のみ。Auth.js などの既存ライブラリを使い自前実装しない |
| 単体テスト | Vitest |
| E2E テスト | Playwright |
| Lint/Format | ESLint + Prettier |
| ディレクトリ | 機能単位 `src/features/<機能名>/` |
| パッケージマネージャ | pnpm |

モバイル・CLI など形態が違う場合は、その形態で一般的な構成を提案し、ユーザーに選ばせる。

## 聞き方のコツ

- 抽象的な問い（「要件は？」）より、具体的な場面（「〇〇さんが月末に請求書を10枚まとめて上げたら？」）で聞く。
- 選択肢を出すときは、機能説明から推測した**具体的な候補**にする。
- 回答に「たぶん」「とりあえず」が出たら、それは【要確認】の候補。確定させるか、未確定として残すかを確認する。
