docs/requirements/requirements.md を更新したい：$ARGUMENTS

まず requirements.md と docs/workflow.md を読むこと。引数がなければ、未確定事項の表と P2・P3 のストーリーを一覧にして、どれから手を付けるか私に聞くこと。

## 進め方

1. 変更の種類を見極めて、私に一言で伝える：新しいストーリーの追加／既存のストーリー・FR・SC の変更／【要確認】の解消／優先度の変更（P2 → P1 など）／スコープ外への移動
2. 書く前に、必要な質問を私にすること。1回に3〜4問ずつ、前の回答を踏まえて深掘りする。エッジケース・失敗時の振る舞い・やらないこと・既存の要件とのぶつかりなど、答えにくい質問ほど価値がある
3. 質問が尽きたら、書き込む前に変更の方針を見せて、私の OK を待つこと：
   - 足す・変える・廃止するストーリー、FR、SC（番号つき）
   - スコープ外・未確定事項の表の増減
   - 影響を受けるプラン・テスト・コード（下の「影響の洗い出し」の結果）
4. OK が出たら requirements.md を更新し、末尾の「変更履歴」に1行足す（日付・変更の要約・変わった番号）

## 書き方のルール

- requirements.md の既存の構成と書き方に合わせる。ストーリーには優先度と Given/When/Then の受け入れシナリオ（異常系を1つ以上）を付ける
- FR は「〜したとき、〜となる」のテスト可能な一文にし、対応するストーリーを書く
- **番号は使い回さない**。新しい FR・SC は既存の最大番号 + 1。要らなくなったものは行を消さず、「（廃止 YYYY-MM-DD：理由）」と書いて残す。意味が変わるほどの変更は、旧番号を廃止して新番号を立てる
- スコープ外に書かれていることを足すときは、スコープ外から外してよいか私に確かめてから動かす
- 「わからない」「後で決める」は【要確認】を付けて本文に残し、未確定事項の表にも足す。推測で埋めない。補った箇所は「（仮置き）」と書く
- 【要確認】が決まったら、本文を書き換え、未確定事項の表からその行を消す
- 選択肢が2つ以上あり後から変えにくい判断や、調べないと決められない論点が出たら、要件に埋めずに /adr の手順で ADR を起票し、未確定事項の表から ADR 番号を参照する

## 影響の洗い出し（既存の FR・SC を変える・廃止するとき）

- `grep -rnE "FR-xxx|SC-xxx"` で、.claude/plans/、docs/adr/、テスト、ソースの参照を集める
- 参照しているプランがあれば、docs/workflow.md でその機能の段階を確かめ、私に伝える
- プランやコードはこのコマンドでは直さない。直す必要があるものを一覧にして、次の一手（`/plan` のやり直し、`/review-plan` など）を提案する

## docs/workflow.md の更新

- 新しく P1 になったストーリーは、「機能ごとの進み具合」に「段階 0／未着手」で行を足す（次の一手は `/plan <機能名と概要>`）
- 変更した要件が進行中・完了済みの機能に関わるときは、その行の「メモ」に「要件変更 YYYY-MM-DD：FR-xxx」と書き、状態を「指示待ち」にして、次の一手に何を決めるかを書く
- P1 から外れたストーリーの行が段階 0 のままなら消す。着手済みなら消さずに私に確認する

## してはいけないこと

- 私の OK の前に requirements.md を書き換えること
- プラン・テスト・アプリのコードを書くこと

終わったら、変わったストーリー・FR・SC の番号、残っている【要確認】、影響を受ける機能と次の一手を短く伝えること。
